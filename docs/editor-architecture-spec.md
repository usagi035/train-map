# 路線図エディター クライアント構成仕様書(v1)

Core の分割と、オンライン共同編集の追加。OpenCode による実装向け。

## 0. この文書について

- 対象は **路線図エディター(Electron アプリ)側**の構成と進め方。シグナリングサーバーは別文書。
- 関連文書:
  - 「路線図エディター オンライン共同編集 要求仕様書」(Host なし / 最大4人 / WebRTC Full Mesh)
  - 「シグナリングサーバー 仕様書(`signaling-server-spec.md`)」
- 表記: 「必須」= 守らなければならない / 「推奨」= 特に理由がなければ従う / 「任意」= してもよい。
- **この文書を書いた時点では、既存のエディターのコードを誰も確認していない。** 既存コードの構成・編集モデル・ファイル形式に関する記述は前提または提案であり、最初に「Phase 0(現状調査)」で事実を確かめ、食い違いがあれば本書より調査結果を優先して、差分を報告する。
- 決まっていないことは「12. 未確定事項」に集めてある。**未確定のことを実装者が勝手に決めてはならない**(記録して質問する)。

## 1. 目的と原則

### 1.1 目的

1. 既存のエディターを、**共通の Core** と、オンライン共同編集用の **Online** に分ける。
2. その上に、最大4人の WebRTC Full Mesh による共同編集を追加する。

### 1.2 原則(優先順に守る)

1. **既存のローカル編集の動作を変えない。** 最優先。リファクタリング中も、完了後も、ローカルで今までどおり使えること。
2. **路線図ファイルの形式を壊さない。** 既存のファイルが引き続き開けること。形式を変える場合は「5. ファイル形式」に従う。
3. **ローカルモードでは通信を一切しない。** ルームを作る・参加するまで、Online のコードを初期化しない(ネットワークに触れない)。
4. **Core はネットワークも画面も知らない。** Electron・DOM・WebSocket・WebRTC に依存しない。
5. **Host を作らない。** 全 Peer が対等で、各 Peer が完全な路線図の状態を持ち、各自がローカルへ保存する(要求仕様書に準拠)。
6. **小さく作り、小さくマージする。** 大きな変更を長いブランチに溜めない。

## 2. Phase 0: 現状調査(コードは変更しない)

最初に次を調べ、`docs/current-architecture.md` にまとめて**報告する**。この段階ではソースコードを変更しない。調査結果を示して確認を取ってから、Phase 1 に進む。

調べる項目:

1. ディレクトリ構成、使用言語(JS / TS)、ビルド方法、使用ライブラリ、テストの有無
2. Electron の構成(Main / Renderer / preload の分担、IPC、`contextIsolation` と `nodeIntegration` の設定)
3. 路線図の**状態の持ち方**(どこに、どんな構造で持っているか)
4. **編集操作の一覧**(駅の追加・移動・削除、踏切、路線、四角形ラベル、色や形の変更など、状態を変えるものすべて)と、それぞれがどこで状態を更新しているか
5. **ID の付け方**(駅・路線などの識別子。連番か、重複しない値か)
6. **ファイル形式**(保存形式の構造、バージョン情報の有無)
7. **Undo / Redo** の有無と実装方式
8. **複数の路線図**の扱い(ウィンドウ、タブなど)と、アプリを閉じるときの挙動
9. 画面の描画とイベント処理が、状態の更新とどの程度混ざっているか(分離のしやすさ)

調査の結果、本書の前提と合わない点(例: 状態が UI と一体になっていて分離が大きな作業になる)があれば、**Phase 1 に進む前に報告する**。

## 3. 目標のモジュール構成

```text
src/
├── core/      路線図の状態、Operation の適用、Undo/Redo、ID の生成
├── file/      路線図ファイルの保存・読み込み(ローカルもオンラインも共通)
├── ui/        エディターの画面
├── online/    シグナリングのクライアント、WebRTC、同期(オンライン専用)
└── main/      Electron の Main Process
```

実際のフォルダ名・ファイル名は、既存の構成に合わせて調整してよい(Phase 0 の結果による)。重要なのは**責務と依存の向き**。

### 3.1 責務

| モジュール | 責務 | 持たないもの |
|---|---|---|
| `core` | 路線図の状態、編集(Operation)の適用、状態の変化の通知、全体の取り出しと読み込み、ID の生成 | 画面、Electron、ファイル、ネットワーク |
| `file` | `core` の状態 ⇄ ファイルの変換、ファイル形式のバージョン管理 | 画面の操作、ネットワーク |
| `ui` | 画面の描画、ユーザー操作を編集として `core` に渡す | 状態の持ち方の詳細、ネットワーク |
| `online` | ルームの作成・参加、WebRTC 接続、Operation と Snapshot の送受信 | 画面の描画、ファイル形式 |
| `main` | ウィンドウ、メニュー、ファイルダイアログ、設定の保存 | 路線図の編集ロジック |

### 3.2 依存の向き(必須)

```text
ui ──> core <── file
 │      ▲
 │      │
 └──> online(遅延読み込み)
```

- `core` は他のどのモジュールにも依存しない。
- `file` は `core` にだけ依存する。
- `online` は `core` にだけ依存する(`ui` や `file` に依存しない)。
- `ui` は `online` を、**ルームを作る・参加するときに初めて**動的に読み込む(`import()`)。
- `core` の中では、`electron`、`window` / `document`、`fetch`、`WebSocket`、`RTCPeerConnection` を使わない。可能なら ESLint の `no-restricted-imports` などで機械的にチェックする(任意)。

### 3.3 「Local」というモジュールは作らない

ローカルモードは、`online` を読み込まない状態のことで、独立したプログラムではない。ローカル専用のコード(保存・読み込み)は `file` にあり、オンライン中も使う。

## 4. Core のインターフェース(契約)

`core` と `online`・`ui` の境界になる部分。名前や型は目安で、既存コードに合わせて調整してよいが、**責務の分担は守る**。

```text
core.getSnapshot()          → 路線図全体の状態(JSON にできる純粋なデータ)
core.loadSnapshot(snap)     → 状態を全体で置き換える
core.dispatch(op, origin)   → Operation を適用する。origin は 'local' か 'remote'
core.subscribe(listener)    → 状態が変わるたびに listener({ operation, origin, ... }) が呼ばれる
```

### 4.1 規則(必須)

1. すべての編集は **Operation として `core.dispatch` を通す**。UI が状態を直接書き換えない。
2. **Operation は JSON にできる純粋なデータ**(関数や DOM オブジェクトを含まない)。
3. **Operation は「確定した編集」の単位**。ドラッグ中の途中経過は Operation にしない(ドラッグは `mouseup` で確定した1回だけ)。要求仕様書の13章に対応。
4. `origin = 'local'` の Operation だけを、`online` が他の Peer へ送る。`origin = 'remote'`(他の Peer から受け取ったもの)は適用するだけで、**再送しない**(ループの防止。要求仕様書の12章)。
5. Operation の適用は**決定的**にする(同じ状態に同じ Operation を適用したら、どの Peer でも同じ結果になる)。時刻や乱数を適用の中で使わない(必要な値は Operation に含める)。
6. 存在しない対象への Operation(すでに削除された駅の移動など)は、エラーにせず**無視してよい**。無視したことはログに残す。

### 4.2 Operation の中身は未確定

Operation の具体的な構造・種類・命名は未確定(要求仕様書26章の4・8)。**Phase 0 で洗い出した編集操作の一覧を元に、別途すり合わせて決める。** Phase 2 に進む前に決定が必要。

要求仕様書にある共通項目の案(確定ではない):

```json
{
  "operationId": "...",
  "peerId": "...",
  "peerOrder": 1,
  "action": "...",
  "targetId": "...",
  "data": {}
}
```

### 4.3 ID の生成

- 駅・路線・踏切などの ID は、**複数の Peer が同時に作っても重複しない値**(`crypto.randomUUID()` など)にする(提案。未確定事項の9)。連番はオンラインで衝突するため使えない。
- 既存ファイルに連番の ID が入っている場合の扱いは、「5. ファイル形式」に従う。

## 5. ファイル形式

- **既存の形式のファイルは、変更後のアプリでも開ける**(必須)。
- 形式の変更が必要になった場合(ID の変更など)は、次の手順を守る。
  1. ファイルに形式のバージョン(例: `formatVersion`)を持たせる。バージョンがない既存ファイルは「バージョン 1(旧形式)」として扱う。
  2. 読み込み時に、古い版から新しい版へ変換する(マイグレーション)。
  3. 新しい形式で保存したファイルは、**古いバージョンのアプリで開けない可能性がある**。保存時または初回起動時に、バックアップを取ることを促す表示を出す(推奨)。
- オンライン共同編集中に保存するのは、**各 Peer が持っている完全な路線図の状態**(要求仕様書22章)。自分の編集分だけではない。
- 保存形式は、ローカルでもオンラインでも**同じ**にする。

## 6. Online モジュール(`online/`)

### 6.1 構成(案)

```text
online/
├── signaling-client    シグナリングサーバーとの WebSocket 通信(プロトコルは signaling-server-spec.md)
├── peer-mesh           Peer ごとの RTCPeerConnection と DataChannel(Reliable)の管理
├── sync                Operation と Snapshot の送受信、Operation ID による重複排除
├── room                ルームの状態(未接続 → 接続中 → 参加中 → 退出)の管理
├── invite              招待情報の生成と解析
└── settings            サーバー URL、ICE サーバーの設定
```

### 6.2 実行する場所(推奨。未確定事項の1)

- WebRTC は **Renderer Process で動かす**ことを推奨する(Chromium の標準 `RTCPeerConnection` が使えるため)。Main Process で動かすには追加のネイティブライブラリが必要になる。
- Renderer にネットワーク機能を持たせるために `nodeIntegration` を有効にしてはならない。`contextIsolation` を有効にしたまま、`preload` で必要最小限の API だけを渡す(設定の保存、ファイルダイアログなど)。
- 追加のライブラリは、原則として入れない(WebRTC は標準 API を使う)。必要になったら理由を添えて確認を取る。

### 6.3 接続の手順(シグナリングサーバー仕様に従う)

1. 作成: `create-room` を送る → `room-created` で `roomId` / `password` / 自分の `peerId` / `peerOrder`(=0)を受け取る。
2. 参加: `join`(`roomId` + `password`)を送る → `joined` で自分の `peerId` / `peerOrder` と、既存の Peer の一覧を受け取る。
3. **新しく入った側が、`joined.peers` に含まれる全員に Offer を送る。** 既存の Peer は `peer-joined` を受け取ったら、その Peer からの Offer を待つ(Answer を返す)。
4. SDP と ICE Candidate は `signal` メッセージで交換する(中身はサーバーが加工しない)。
5. DataChannel が開いたら、それ以降の Operation・Snapshot は **DataChannel でのみ**送る。**シグナリングサーバーには、SDP と ICE 以外を送ってはならない。**
6. **参加中は WebSocket を維持する**(切断は退出として扱われる)。
7. `peer-left` を受け取ったら、その Peer を参加者から外し、対応する接続を閉じる。
8. `peerOrder` は、同じオブジェクトへの競合の優先順位(小さいほうが優先)に使う。**番号が 0〜3 とは限らない**(退出・再参加で増える)。大小比較だけに使う。

### 6.4 DataChannel

- 編集用の DataChannel は **Reliable かつ順序保証あり**にする(要求仕様書8.2)。
- 送信するのは JSON(文字列)。サイズが大きい Snapshot の分割送信が必要かどうかは Phase 4 で確認する。

### 6.5 Snapshot(参加時の初期同期)

- 新しい Peer は、参加後に既存の Peer の1人から路線図全体を Snapshot として受け取る。
- **誰に要求するか、送信中に発生した Operation をどう扱うかは未確定**(未確定事項の2・3)。案: 参加直後に `peerOrder` が最小の既存 Peer へ要求する。Phase 4 に入る前に決める。

### 6.6 Operation の同期と順序

- Operation ID による**重複排除**を行う(処理済みの ID を覚えておき、同じ ID の Operation は二重に適用しない。要求仕様書16章)。
- 全体の順序付け(未確定事項の5)と、同一オブジェクトの競合の解決(`peerOrder` が小さいほうを優先。要求仕様書15章)は、Phase 5 に入る前に具体的な方式を決める。CRDT や OT のような複雑な方式は採用しない。

## 7. UI の要件(オンライン関連)

見た目の細部は既存のエディターのデザインに合わせる。ここでは機能だけを定める。

1. **メニュー**に「共同編集」を設け、「ルームを作成」「ルームに参加」を置く。
2. **サーバー設定**: シグナリングサーバーの URL を入力・保存できる。**既定値は持たない。** 未設定のまま「作成」「参加」を押したら、設定が必要なことを案内する。
3. **ICE サーバー設定**: STUN / TURN を追加・変更できる。既定の STUN を1つ入れておく案(未確定)。
4. **ルーム作成後**: 招待情報(サーバー URL、Room ID、パスワードをまとめた文字列)を表示し、コピーできる。
5. **参加**: 招待情報を貼り付けて参加できる。Room ID、パスワード、サーバー URL を個別に入力する方法も用意する。
6. **オンライン中の表示**: 共同編集中であること、参加者の人数、各 Peer の接続状態が分かる。ローカルモードとの違いが一目で分かるようにする。
7. **退出時**: 路線図の保存を確認する(要求仕様書22章)。

   ```text
   路線図を保存しますか?
   [保存] [保存しない] [キャンセル]
   ```

   「保存」を選んだら、その時点で自分が持っている**完全な路線図の状態**を保存する。
8. エラー(サーバーにつながらない、パスワードが違う、満員、サーバーが停止した)は、利用者に分かる言葉で表示する。シグナリングサーバーのエラーコードとの対応は実装時に決める。

## 8. 招待情報

- 参加者は作成者と**同じシグナリングサーバー**につなぐ必要があるため、招待情報には、サーバーの URL、Room ID、パスワードの3つを含める。
- 形式は未確定。案: `railmap-collab://join?server=<URLエンコードした wss URL>&room=<roomId>&pw=<password>` のような1つの文字列。最初は「文字列をコピーして貼り付ける」方式でよく、カスタムプロトコルの登録(リンクのクリックで起動)は任意。
- 招待情報の解析では、サーバー URL が `wss://` であることを確認する(`localhost` / `127.0.0.1` への `ws://` は開発用として許可してよい)。
- パスワードをログに出力しない。

## 9. ブランチ運用と Phase

### 9.1 リポジトリ

- **エディター本体**: 今のリポジトリのまま、ブランチで進める。新しいリポジトリは作らない。
- **シグナリングサーバー**: **新しいリポジトリ**にする(`package.json`・配布が別のため)。

### 9.2 ブランチの原則

1. 最初に、今の main に**タグ**を付ける: `git tag pre-collab`。リモートにも push する(または別の場所に複製を取る)。いつでもここへ戻れるようにする。
2. 作業は main から切った**短いブランチ**で行い、**小さく、早く、頻繁に main へマージ**する。長く生きるブランチは作らない。
3. Online は**既定でオフ**にしておく。途中でマージしても、ローカルの使い方は変わらない。
4. main にマージする条件: 「ローカルで今までどおり使える」ことを、確認項目(下記)で確かめてあること。
5. 1つのブランチで、リファクタリング(動作を変えない変更)と、機能追加を混ぜない。

### 9.3 Phase

| Phase | 内容 | ブランチ(案) | 完了条件 |
|---|---|---|---|
| 0 | 現状調査(コード変更なし) | (なし) | `docs/current-architecture.md` を提出し、確認を得る |
| 1 | **Core の分割**。動作は変えない | `refactor/core-split` | 3.2 の依存の向きを満たす。ローカルの全機能が従来どおり。既存ファイルが開ける。main にマージ |
| 2 | **編集の Operation 化**。すべての編集を `core.dispatch` 経由にし、`subscribe` で通知する。ローカルのみ。Undo/Redo は既存の挙動のまま | `refactor/operations` | Operation の構造が決まっていること(4.2)。ローカルの動作が変わらない。main にマージ |
| 3 | **オンライン基盤**。シグナリング接続、WebRTC 接続、DataChannel で疎通確認(hello のやり取り)まで。路線図はまだ同期しない | `feature/collab-connection` | 2〜4つのアプリ間で DataChannel が開く。参加・退出が正しく伝わる |

| 6 | **退出時の保存、UI の仕上げ、エラー表示** | `feature/collab-ui` | 7章の要件を満たす |
| 7 | **再接続、Undo/Redo のオンライン対応** | (未確定事項が決まってから) | — |

各 Phase の終わりに、**何をしたか、確認したこと、残っている課題**を報告する。

### 9.4 ローカルでの回帰確認

Phase 1 以降、main にマージする前に、次を確認する(自動テストにできるものはテストにし、できないものは手順を `docs/regression-checklist.md` に残す)。

- Phase 0 で洗い出した**すべての編集操作**が、従来どおり動く
- 保存して開き直して、同じ状態になる
- **既存のファイル**(Phase 0 の時点で保存しておいたサンプル)が開け、見た目が変わらない
- 複数の路線図を開いたとき、アプリを閉じるときの挙動が変わらない
- ローカルモードで、**ネットワーク通信が発生しない**(Online が読み込まれない)

## 10. テスト

- `core` は純粋なデータの操作なので、**単体テスト**を書く(Operation を適用した結果、決定的であること、存在しない対象の Operation が無視されること、`getSnapshot` と `loadSnapshot` が往復で一致すること)。
- 既存のテストの仕組みがあればそれに従う。なければ `node:test` を使う(追加の依存を入れない)。
- `online` の同期ロジック(重複排除、競合の優先順位)は、WebRTC から切り離した形でテストできるようにする(送受信を差し替えられる設計)。
- 2〜4つのアプリを起動して確認する手順を、`docs/online-manual-test.md` に残す。

## 13. OpenCode への指示

1. **Phase 0 から始める。** コードを変更する前に、調査結果(`docs/current-architecture.md`)を提出し、確認を得る。
2. 本書の前提と実際のコードが食い違う場合は、勝手に直さず**報告する**。
3. 未確定事項(12章)や、本書に書かれていない判断が必要になったときは、**勝手に決めず、質問する**か、`docs/decisions.md` に選択肢と理由を記録して確認を待つ。
4. **既存の動作と保存形式を変えない**(1.2 の原則)。リファクタリングと機能追加を同じブランチに混ぜない。
5. 各 Phase は、9.3 のブランチで作業し、完了条件を満たしてから報告する。
6. 依存ライブラリは原則追加しない。必要な場合は理由を添えて確認を取る。
7. シグナリングサーバーに SDP と ICE 以外のデータ(Operation、Snapshot、路線図の内容)を送るコードを書かない。
8. パスワード、SDP、ICE Candidate の内容をログに出さない。
9. シグナリングサーバー側に変更が必要だと分かったら、`signaling-server-spec.md` を直接変えず、変更案を報告する。
